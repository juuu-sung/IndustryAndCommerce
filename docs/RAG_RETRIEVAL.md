# NOx 문서 검색 기반 · 구현과 첫 비교 결과

2026년 10월 14일 로컬 구현·검증 기록입니다. 기존 보고서의 수치 도구와 함께 사용할 **문서 검색 API**를 추가했습니다. 문서 위치·버전을 반환하는 단계이며, 검색 결과를 Gemini 답변이나 보고서 개정에 자동 연결하는 단계는 아직 구현하지 않았습니다.

위 내용은 첫 검색 단계의 기록입니다. 이후 [검색 보완·근거 보고서·Agent 구현](COPILOT_WORKFLOW_20261014.md)을 추가했습니다. 같은 추가 질문 20개에서 기존 Keyword 55%→개선 Keyword 65%였으며 보고서의 수치/문서 연결과 검토/재개까지 구현했습니다. 실제 Gemini 호출과 의미적 근거 검증은 남아 있습니다.

## 검색 구성

| 방식 | 실제 구현 |
| --- | --- |
| Keyword | 한국어 문자 조각·정규화·일부 한영 용어 대응 + 로컬 BM25 |
| Vector | `intfloat/multilingual-e5-small` 실제 추론, 정확한 코사인 검색 |
| Hybrid | 각 검색 상위 20개를 RRF로 결합, 최종 상위 5개 |

임베딩은 **384차원**, `query: `/`passage: ` 접두사, 평균 풀링·L2 정규화를 사용합니다. 모델·토크나이저 revision은 `614241f622f53c4eeff9890bdc4f31cfecc418b3`로 고정했습니다. 본문 256토큰·중첩 32토큰이며 제목·접두사까지 512토큰 안에 들어가는지 검사합니다. 사전학습 모델의 추론으로, NOx 모델 재학습은 하지 않았습니다.

첫 비교 전에 코사인 하한 0.80, RRF k=60을 고정했습니다. Hybrid는 의미 검색 후보가 전혀 없으면 키워드만으로 결과를 내지 않습니다. 이 규칙도 모든 무관 질문을 걸러내는 보장은 아닙니다.

Docker가 실행 중이지 않고 pgvector 확장이 없어서 **로컬 정확 검색**으로 먼저 구현했습니다. PostgreSQL 전문 검색·pgvector·재순위 모델은 아직 도입하지 않았습니다. 임베딩 워커는 외부 LLM API를 호출하지 않으며 기존 NOx Python 환경의 패키지를 교체하지 않습니다.

## 첫 평가 결과

질문 50개를 검색 결과를 보기 전에 **개발 30개 / 후속 평가 20개**로 나눴습니다. 개발에는 답할 수 있는 질문 26개와 근거가 없는 질문 4개, 후속 평가에는 각각 16개와 4개가 있습니다. 개발 Recall@5에서 무근거 질문의 잘못된 결과 반환률을 차감하는 기준으로 **Keyword 후보를 선정하고 잠금 파일을 저장한 뒤** 후속 평가를 실행했습니다. 코사인 임계값은 이번에 튜닝하지 않았습니다.

| 검색 방식 | 개발 Hit@5 | 후속 평가 근거 발견 | 후속 Recall@5 | 후속 MRR | 근거 없는 질문 처리 | 후속 지연 p50 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Keyword | 76.9% | **12 / 16** | **75.0%** | **0.549** | 3 / 4 | 211ms |
| Vector | 65.4% | 6 / 16 | 37.5% | 0.203 | 4 / 4 | 137ms |
| Hybrid | 69.2% | 11 / 16 | 68.8% | 0.422 | 4 / 4 | 238ms |

- **Hit@5**: 등록한 정답 근거 중 하나라도 상위 5개에 있는 질문 비율입니다.
- **Recall@5**: 질문별로 필요한 근거 그룹 중 찾은 비율의 평균입니다. 이 평가에서는 Hit와 Recall 수치가 같았으며, 일반적으로 항상 같지는 않습니다.
- **MRR**: 처음 찾은 정답 근거의 순위가 높을수록 커집니다.
- **근거 없는 질문 처리**: 결과를 반환하지 않고 기대한 상태를 내는지 확인합니다. 4개 중 3개는 수치·기관 자료·법적 판정에 대한 명시적 분기 규칙으로 처리하므로, 4/4를 일반적인 환각 방지 정확도라고 부를 수 없습니다.

워커·모델을 예열하고 매번 질의 벡터 캐시를 비운 CPU 검색 시간입니다. 파일 무결성 검사를 포함하며 모델 최초 로딩·HTTP 전송·LLM 생성 시간은 제외합니다. 재확인 실행의 p95는 Keyword 277ms, Vector 259ms, Hybrid 311ms였습니다. 검색 방식의 실행 순서는 질문마다 바꿨습니다. 재확인 중에는 회귀·HTTP 검사도 실행되어 부하를 통제한 지연 벤치마크가 아니며 서비스 SLA로 사용하지 않습니다.

**좋았던 점:** 연구 타깃·전월 계산·단위·검증 한계 같은 한국어 프로젝트 질문에서 키워드 검색이 많은 근거를 찾았습니다. **남은 문제:** 영문 SCR·SNCR 자료로 답해야 하는 질문은 모든 방식에서 약했습니다. 키워드는 요리 질문에도 무관한 결과를 반환했습니다. 임베딩 하한만으로 근거 없음 처리가 해결되지는 않았습니다.

정답 근거는 AI가 원문 문자 구간을 대조해 등록했습니다. 독립 담당자·전문가 검토는 남아 있습니다. 등록 구간을 완전히 포함해야 정답으로 세며, 다른 문서의 동등한 근거가 정답에 등록되지 않았으면 낮게 집계될 수 있습니다. 예를 들어 암모니아 슬립 질문은 관련 매뉴얼 페이지가 검색됐지만 지정한 Fact Sheet 구간은 찾지 못했습니다. 이 수치는 **등록 근거 검색 성능**이며 자연어 답변의 정오 판정이 아닙니다.

초기 목표 Hit@5 80%는 아직 달성하지 못했습니다. 현재 API 기본 방식은 비교용 Hybrid이며, 개발에서 선정한 Keyword를 자동 배포하지 않았습니다. LLM 자동 답변도 활성화하지 않았습니다. 최초 비교 후 원문 마지막 줄의 표시 오류를 수정하고 동일 질문으로 재확인했으며 근거 발견 수는 같았습니다. 공개 결과 v2에는 이전 평가 ID와 `test_results_previously_observed=true`를 기록했습니다. 이 재실행을 새 독립 평가로 해석하지 않으며, 다음 최종 확인에는 새 질문을 사용해야 합니다.

## API와 예시

| API | 반환 |
| --- | --- |
| `GET /api/rag/status` | 색인 준비 상태·문서/청크 수·임베딩/검색 버전 |
| `GET /api/rag/documents` | 현재 접근 허용 문서의 출처·버전·범위 |
| `POST /api/rag/search` | 문서·버전·해시·페이지/절·문자 위치·본문·검색 점수 |

```json
{
  "query": "NOx 연구 타깃은 무엇을 월별 평균한 값인가요?",
  "method": "keyword",
  "top_k": 5,
  "scope": "project_method"
}
```

`method`는 `keyword` / `vector` / `hybrid`를 지원합니다. `document_ids`, `scope`, `as_of`를 선택적으로 받습니다. 범위와 공개/제한 문서는 순위 계산 전에 필터링합니다. `as_of`는 **알려진 발행일** 기준이며 발행일 미상 문서는 제외합니다. 실제 설비 적용 기간·법령 효력을 판정하는 필드는 아닙니다. 현재는 로컬 허용 목록 기반이며 사용자 인증·조직별 접근 제어는 후속 기능입니다.

| 질문 예 | 현재 처리 |
| --- | --- |
| “NOx 연구 타깃의 정의는?” | 프로젝트 문서의 근거와 위치 반환 |
| “SCR의 일반 점검 요소는?” | 일반 기술자료 범위를 지정해 검색 가능; 특정 호기의 실제 원인은 확정하지 않음 |
| “영동 2025년 10월 예측값은?” | `requires_numeric_tool`; 숫자를 문서 검색으로 생성하지 않음 |
| “영동 SCR 고장을 확정해 줘” | `requires_provider_evidence` |
| “국내 법정 NOx 허용기준 수치는?” | `requires_verified_regulation` |

위 분기는 제한된 표현을 검사하는 규칙이며 Agent의 도구 선택·실행은 아닙니다. 검색 상태 `evidence_found`도 근거가 충분하거나 답변이 맞다는 인증이 아닙니다. 결과를 외부로 그대로 표시할 때는 문서 이용 조건과 인용 분량을 별도로 지켜야 합니다.

## 검증과 재현

신규 RAG 검사 **42개**, 기존 검사 포함 **348개 통과 / 건너뛴 검사 0개**입니다. 원문·청크·벡터·버전 변경 차단, 권한/발행일 필터, 중복 JSON 키·NaN·부적합 요청, 근거 구간 평가, 워커 종료 후 기존 예측 유지, 실제 E5 검색을 확인했습니다. 기존 Pandas FutureWarning 1건이 있으며 실패는 없습니다.

별도 임시 포트에서 실제 HTTP로 검색 상태·문서 목록·프로젝트/기술 문서 검색·수치 도구 요구·기존 예측·보고서 생성/조회·HTML을 확인했습니다. 보고서는 여전히 `rag_status=not_enabled`로 표시합니다. [HTTP 검증 기록](generated/rag_http_verification.json)

현재 로컬 자료가 준비된 환경에서 실행합니다.

```bash
cd NOx_corrected
python -m pytest --require-local-assets -q
MPLCONFIGDIR=/tmp/nox-mpl python scripts/check_rag_http.py
python -m nox.copilot.rag.evaluation \
  --output data/runtime/copilot/rag/evaluation_new_run
```

평가 출력은 기존 잠금/결과를 덮어쓰지 않으며 재평가에는 새 디렉터리를 사용합니다. 반복해서 같은 질문을 실행해도 새 독립 평가가 되지는 않습니다. 원문·모델·색인·런타임 결과는 Git에서 제외했습니다. 코드는 `nox/copilot/rag/`, 선택적 패키지는 `requirements-rag.txt`, 실제 자산 수집은 `scripts/prepare_rag_assets.py`에 있습니다. 이번 검증에서는 선택적 패키지를 `data/runtime/copilot/rag/deps`에 분리 설치했습니다.

## 다음 우선순위

1. 정답 근거의 동등한 대안을 담당자가 검토하고 질문·근거 버전을 갱신합니다.
2. 개발 질문에서 문서 범위 선택·한영 용어 확장·영문 기술 질문 보완을 비교합니다. 모든 범위를 섞은 검색과 구분해 측정합니다.
3. 청크 전략·제목 영향·재순위 모델을 개발 질문으로 비교하고, 새로운 질문에서 확인합니다. 무관 질문도 더 다양하게 늘립니다.
4. 검증된 수치와 문서 근거를 보고서의 `fact_refs`·`citation_refs`에 연결하고 Gemini 답변의 근거 충실성을 별도로 평가합니다.
5. 이후 Agent 도구 실행·승인/재개, 새 조건 추론·신규 호기 보고서를 각각 검증합니다.

RAG 검색을 추가한 것이 NOx 급등 예측 오차나 측정 유효성 문제를 해결한 것은 아닙니다. 실제 호기 운전·저감설비·측정 유효성 기록은 기관 자료 확보와 별도로 진행합니다.
